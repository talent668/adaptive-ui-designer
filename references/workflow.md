# Route and implementation

## Choose once

- **Demo first:** prepare one project-specific direction, with useful alternatives, then show an adjustable preview. Implement after the user confirms it.
- **Direct:** follow an explicit request to generate or change the page directly.
- **Prompt only:** prepare the reviewed design and portable handoff; do not generate an application.

Existing confirmation, a requested scoped fix, and skill maintenance do not restart route selection. A request to choose the design for the user does not itself require a technical questionnaire. Continue independent inspection while an optional preference is pending.

## Inspect the project

Read manifests, routes, entry points, representative components, tokens, fonts and relevant commands. Preserve the current framework, data contracts and confirmed brand. For a new project use the requested stack, otherwise choose the smallest appropriate implementation.

Establish the audience, primary task/action, content shape, language, device range and appearance requirements. Mark inferred context and synthetic examples honestly.

## Prepare a reviewable design

Write `designIntent` before arranging components. Prioritize the content and next action that earn the first screen. Build actual scene markup, not a generic dashboard with renamed labels. A representative working slice is sufficient for design selection; several complete alternative apps are unnecessary.

Default to one recommendation with detailed controls closed. Explain each alternative's benefit and tradeoff after it can be seen. Translate ordinary comments into design revisions without requiring token values from the user. Preserve explicit manual choices across revisions.

## Continue after confirmation

Read `#confirmedDesignRecord` or the explicit chat selection. Check project, revision, current/stale status and pending feedback. Capture current layout, type, colors, material, geometry, controls and scope before editing. Do not require copying a prompt or approving the same design again.

Implement in the native project structure: Vue SFCs, React components, semantic HTML/CSS/JS, or the existing stack. Use reusable tokens and components rather than embedding a screenshot or the studio in the product. Keep scene assets and requested interactions. Buildless previews do not authorize framework migration.

The generator is an optional starter for a new standalone page. It cannot establish that a real repository, its APIs, or a custom scene's business behavior was integrated.

## Capability limits

Use equivalent host tools. A terminal-only host can inspect source and deliver a runnable preview, but must disclose unverified rendering. Native skill discovery, source checks, builds and browser interaction are separate evidence. Do not create an external account, publish, or invoke another provider to compensate for a missing preview tool.
